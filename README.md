# SimPoint Backend

[![CI](https://github.com/Al1veeee/simpoint-backend/actions/workflows/ci.yml/badge.svg)](https://github.com/Al1veeee/simpoint-backend/actions/workflows/ci.yml)

REST-сервис и служебный Telegram-бот для точки продаж сим-карт SimPoint (Москва, дилер Т2, МТС, Билайн, МегаФон и Йота): учёт продаж и услуг, склад сим-карт, тарифы, клиенты, отчёты.

Абонентов оформляют в приложениях операторов. Этот сервис ведёт учёт точки поверх них: выручка по всем пяти операторам в одном месте, услуги, которых в операторских приложениях нет (ремонт, настройка, платежи), остатки сим-карт и работа каждого продавца. Продавцы вносят продажи через Telegram-бота кнопками.

Главная предметная особенность: по каждому оператору точка выполняет разный набор услуг. Например, замену IMEI делают только для МегаФона и Йоты, перенос номера только для Т2, а переоформление договора не делают ни для кого. Эта матрица хранится в базе, редактируется через API и проверяется при оформлении каждой продажи.

## Стек

| Слой | Технологии |
|------|-----------|
| Язык и фреймворк | Java 21, Spring Boot 3.5 |
| Веб | Spring Web MVC, Bean Validation, springdoc-openapi (Swagger UI) |
| Данные | Spring Data JPA (Hibernate 6), PostgreSQL 16, Flyway |
| Безопасность | Spring Security, JWT (jjwt), BCrypt, роли ADMIN и SELLER |
| Telegram | Собственный клиент Bot API на RestClient, long polling |
| Тесты | JUnit 5, Mockito, AssertJ, MockMvc, Testcontainers |
| Инфраструктура | Docker, Docker Compose, GitHub Actions |

## Архитектура

```
web/          REST-контроллеры, обработка ошибок (RFC 7807 ProblemDetail)
service/      бизнес-логика, транзакции
repository/   Spring Data JPA, JPQL-агрегаты для отчётов, Specifications для фильтров
domain/       JPA-сущности и enum-ы
dto/          records запросов и ответов с валидацией
security/     JWT: выпуск, проверка, фильтр
telegram/     бот: клиент Bot API, long polling, роутер, мастер оформления продажи
config/       Security, OpenAPI, типизированные настройки
```

Бот вызывает те же сервисы, что и REST API, поэтому все бизнес-правила (матрица услуг, списание сим-карт, отмена) работают одинаково в обоих каналах.

Модель данных: `user_account`, `tariff`, `sim_card`, `customer`, `operator_capability`, `sale`, `sale_item`. Схема создаётся миграциями Flyway, Hibernate работает в режиме `validate`.

## Что умеет

- Вход по логину и паролю, JWT на 8 часов, разграничение по ролям.
- Склад сим-карт: приход партией по ICCID, фильтры по оператору и статусу, остатки, брак. Двойная продажа одной сим-карты исключена оптимистической блокировкой.
- Тарифы: CRUD для администратора, деактивация вместо удаления, чтобы не ломать историю продаж.
- Матрица услуг оператор × услуга с заметками, редактируется администратором.
- Продажи: несколько позиций в одном чеке, автоматическая проверка услуги по матрице, списание сим-карты со склада, цена позиции из тарифа по умолчанию, отмена с возвратом сим-карты на склад.
- Отчёты: количество продаж и выручка за период, разбивка по операторам и по видам услуг.

## Telegram-бот для продавцов

Продавец оформляет продажу кнопками, без приложения и без браузера:

```
🧾 Новая продажа
  → оператор: Т2 · МТС · Билайн · МегаФон · Йота · без оператора
  → услуга: показываются только те, что точка делает для этого оператора
  → сим-карта: кнопкой из списка на складе или последними цифрами ICCID
  → тариф → цена (по тарифу одной кнопкой или вручную)
  → чек: можно добавить ещё позицию
  → 💵 Наличные / 💳 Карта / 📲 Перевод
  → кто оформил: сотрудник из списка или «Другой» с вводом имени — продажа оформлена
```

Разделы меню:

- **📊 Сегодня**: выручка и количество продаж, разбивка по операторам, услугам и по тому, кто оформлял; переключение на «с начала месяца».
- **📦 Склад**: остатки по операторам, приём партии и список карт. ICCID присылаются списком; удобно сканером штрихкодов в Telegram на компьютере. У каждой непроданной карты кнопки «Брак» / «Вернуть на склад» и «Удалить» (только администратор и только для карт, которых нет в истории продаж).
- **🕘 Последние продажи**: отмена с подтверждением. Продавец отменяет только свои продажи, администратор любые; сим-карты возвращаются на склад.

Безопасность:

- бот отвечает только сотрудникам, привязавшим аккаунт командой `/link логин пароль`; сообщение с паролем бот сразу удаляет;
- `/password новый_пароль` меняет свой пароль, администратор может задать пароль сотруднику: `/password логин новый_пароль`; эти сообщения бот тоже удаляет;
- после 5 неверных попыток вход из чата блокируется на 15 минут;
- работает только в личных чатах, токен бота не попадает в логи.

Подключение:

1. Создать отдельного бота в [@BotFather](https://t.me/BotFather) (не клиентского), получить токен.
2. Задать `TELEGRAM_ENABLED=true` и `TELEGRAM_BOT_TOKEN=<токен>` в окружении или `.env`.
3. Запустить сервис. Бот работает через long polling, публичный HTTPS-адрес не нужен.
4. Каждый сотрудник пишет боту `/link логин пароль`.

## Конфигурация и секреты

Секретов в репозитории нет: всё задаётся переменными окружения. Шаблон лежит в `.env.example`, заполненный `.env` в git не попадает.

| Переменная | Обязательна | Назначение |
|------------|-------------|-----------|
| `JWT_SECRET` | да | Ключ подписи JWT, от 32 символов. Без него приложение не запустится |
| `ADMIN_PASSWORD` | при первом запуске | Пароль администратора `admin` (имя меняется через `ADMIN_USERNAME`). Применяется, только если у него ещё нет рабочего пароля |
| `TELEGRAM_BOT_TOKEN` | если `TELEGRAM_ENABLED=true` | Токен бота от @BotFather |
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | нет | Подключение к PostgreSQL, по умолчанию локальная база `simpoint` |

Сгенерировать секрет: `openssl rand -base64 48`.

В Docker Compose порты базы и приложения открыты только на `127.0.0.1`.

## Запуск

Docker Compose, всё в контейнерах:

```bash
cp .env.example .env   # заполнить JWT_SECRET и ADMIN_PASSWORD
docker compose up --build
```

Локально с уже запущенным PostgreSQL:

```bash
createdb simpoint
export JWT_SECRET="$(openssl rand -base64 48)" ADMIN_PASSWORD=придумайте-пароль
mvn spring-boot:run
```

В IntelliJ IDEA переменные задаются в Run → Edit Configurations → Environment variables.

После старта:

- Swagger UI: http://localhost:8080/swagger-ui.html
- OpenAPI JSON: http://localhost:8080/v3/api-docs
- Health: http://localhost:8080/actuator/health

Миграция `V3__demo_data.sql` создаёт аккаунты `admin` и `seller` и демонстрационные сим-карты. Пароли этих аккаунтов были в открытом виде в истории проекта, поэтому миграция `V7__disable_demo_passwords.sql` отключает их: войти можно только с паролем из `ADMIN_PASSWORD` или заданным через `/password` в боте. Реальные тарифы операторов добавляет миграция `V6__real_tariffs.sql`, список сотрудников для поля «кто оформил» лежит в таблице `performer` (`V5__performers.sql`).

Готовые запросы для IntelliJ HTTP Client лежат в `http/requests.http`.

## API

Все эндпоинты, кроме `/api/v1/auth/login`, требуют заголовок `Authorization: Bearer <token>`.

| Метод | Путь | Описание | Роль |
|-------|------|----------|------|
| POST | `/api/v1/auth/login` | Получить JWT | |
| GET | `/api/v1/capabilities` | Матрица услуг по всем операторам | любая |
| GET | `/api/v1/capabilities/{operator}` | Услуги одного оператора | любая |
| PUT | `/api/v1/capabilities/{operator}/{serviceType}` | Включить или выключить услугу | ADMIN |
| GET | `/api/v1/tariffs?operator=` | Активные тарифы | любая |
| POST, PUT, DELETE | `/api/v1/tariffs`, `/api/v1/tariffs/{id}` | Управление тарифами | ADMIN |
| POST | `/api/v1/sim-cards/batch` | Оприходовать партию | любая |
| GET | `/api/v1/sim-cards?operator=&status=&page=&size=` | Поиск по складу | любая |
| GET | `/api/v1/sim-cards/stock` | Остатки по операторам | любая |
| PATCH | `/api/v1/sim-cards/{id}/defective` | Пометить брак | любая |
| POST, GET, PUT | `/api/v1/customers` | Клиенты | любая |
| POST | `/api/v1/sales` | Оформить продажу | любая |
| GET | `/api/v1/sales?from=&to=` | Продажи за период | любая |
| GET | `/api/v1/sales/{id}` | Продажа с позициями | любая |
| POST | `/api/v1/sales/{id}/cancel` | Отменить продажу | любая |
| GET | `/api/v1/reports/sales?from=&to=` | Сводка за период | любая |

Пример оформления продажи:

```json
POST /api/v1/sales
{
  "paymentMethod": "CARD",
  "items": [
    {"serviceType": "SIM_SALE", "operator": "T2", "simCardId": 1, "tariffId": 1},
    {"serviceType": "PHONE_SETUP", "price": 300, "description": "Настройка телефона"}
  ]
}
```

Если в позиции указать услугу, которую точка не делает для этого оператора, сервис вернёт `409 Conflict` с объяснением:

```json
{
  "type": "about:blank",
  "title": "Нарушение бизнес-правила",
  "status": 409,
  "detail": "Услуга «Замена IMEI» не выполняется для оператора МТС"
}
```

## Тесты

```bash
mvn verify
```

- Юнит-тесты сервисов и JWT: Mockito, без базы. Отдельно проверяются правила паролей и создание первого администратора.
- Тесты бота: мастер продажи проходит сценарии целиком (сим-карта с тарифом, услуга без оператора, отказ по матрице, ошибка при оформлении, устаревшая кнопка), разбор сумм и форматирование.
- Интеграционный тест `SalesFlowIntegrationTest`: поднимает PostgreSQL в Testcontainers и прогоняет сценарий целиком: вход, приход партии, создание тарифа, продажа, проверка списания, отказ по матрице, отчёт, отмена, возврат на склад; заодно проверяет, что опубликованные демо-пароли не работают. Без Docker тест пропускается.
